# 结构光与 Python 调优

Python 是否慢，需要看实际计算在哪里。本轮保留 Python 编排和 NumPy/OpenCV 内核，优先拆分法向计算的大数组及独立行块，没有整体重写为另一门语言。

## 当前执行状态

| 工作 | 项目层面的执行方式 | 是否已新增内部并行 |
| --- | --- | --- |
| 结构光重建子进程 | 与 GUI 独立运行的单个 QProcess | 仅表示进程隔离 |
| 站点、曝光和输入图像读取/解码 | 子进程内依次循环 | 否 |
| 三角化数据块 | NumPy 批量计算，按块推进 | 否，没有块任务池 |
| 大点图的 organized normal | 行块线程池 | **是，最多 4 个工作线程** |
| 小点图或单线程模式的法向 | 直接计算或逐块计算 | 否 |
| 各站融合、体素分组和最终导出 | 顺序调用 NumPy/文件接口 | 否，没有站点或融合线程池 |
| Mitsuba 各站点、曝光和图案渲染 | 单独子进程，外层顺序推进 | 否，未新增多帧池 |
| COLMAP 各命令 | 依次启动/等待外部引擎 | 引擎内部并行/GPU 由其配置决定 |

NumPy/OpenCV/Mitsuba/COLMAP 内部可能使用自己的本地线程。本表仅标记项目代码明确增加的并行，不能把所有本地算子都当作单线程，也不能把批量数组操作当作多个项目任务同时运行。

## 1. 法向估计按行块并行

原实现一次堆叠每个有效点的 5×5 邻域，产生 `N×25×3` 的 float64 位移数组，随后还要构造有效性掩码、协方差和特征向量。约 123 万有效点时，仅位移数组就接近 737 MB，整个进程峰值更高。

新实现保留原来的局部 PCA、可靠性判定和朝向相机的符号规则。行块保留上下两行 halo，保证相邻块边界仍使用完整的 5×5 邻域；各块只把自己的中心区域写回原位置。

- 块高最多 64 行，目标中心区域约不超过 65,536 像素，另加 halo。
- 自动工作数由 CPU 数、行块数和 4 的上限共同决定。
- 任一维小于 3、高度不超过 64 或总像素数小于 65,536 时走直接计算路径。
- `workers=1` 使用串行分块；`workers=0` 自动选择。该参数属于法向函数 API，不是 C++ 预处理线程数。
- 调用方在块交付时检查取消，取消未开始的任务并等待当前小块收尾。

## 2. 耗时与内存变化

| 点图 | 原实现 | 自动分块并行 | 加速比 |
| --- | ---: | ---: | ---: |
| 512×384 | 0.706 s | 0.255 s | 2.77× |
| 1280×960 | 4.958 s | 1.536 s | 3.23× |

1280×960 的进程峰值工作集从 2.376 GB 降为 0.570 GB，减少约 76%。单线程分块约 4.892 s、峰值 0.266 GB：它主要节省内存，不能获得相同的多核吞吐收益。各模式的输出 SHA-256 完全相同，包含深度台阶及缺失像素的验证。

这些是有较多有效像素的合成点图。实际扫描的有效像素比例、分辨率和文件开销不同，整体速度需要重新测量。已有 256×192 扫描回放使用小图串行路径，整条解码流程未观察到可靠的显著加速。

## 3. 站点与拍摄流程仍有串行工作

结构光重建按站点循环，每站再按曝光和图像循环，三角化也按块顺序执行；只有满足条件的单站法向阶段进入本轮新增的线程池。最终全站融合仍是顺序调用。

VTK 拍摄由其拥有上下文的 GUI 线程逐帧渲染、读回并保存 PNG；事件循环分帧调度不等于多线程同时渲染。Mitsuba 使用独立进程，但站点、曝光和图案也是外层串行，当前固定使用 `scalar_rgb`。尚未启用项目级多帧并行，也没有完成 LLVM/CUDA 变体切换；`scalar_rgb` 的名称不等于整个引擎只有一个 OS 线程。

直接并发大量站点会同时保留多组图像、坐标、点图和法向临时数组，容易抵消分块带来的内存节省。后续若增加站点池，需要先定义共享线程预算和未完成任务上限。

## 4. 哪些部分值得迁移 C++

| 部分 | 当前判断 |
| --- | --- |
| COLMAP Python 编排 | 计算已经在外部本地引擎，重写调度层收益有限 |
| 解码与三角化 | 主要是 NumPy/OpenCV 本地计算，先测复制、分块和 I/O |
| organized normal | 本轮已通过分块和线程池获得收益，暂未迁移语言 |
| 超大点云体素融合 | 可评估 C++ 排序/哈希归并内核，但必须保留权重、法向兼容与输出语义 |
| Mitsuba 包装 | 优先验证执行变体和缓存策略，重写 Python 包装不等于更换渲染内核 |

如果继续迁移，优先暴露接收连续数组的 C++ 内核，并验证 GIL、内存所有权和结果一致性。不要通过逐点 Python list/JSON 往返抵消本地计算收益。

代码入口：`core/reconstruction/structured_light/normals.py`、`pipeline.py`、`mitsuba_renderer.py`，以及 `colmap_reconstruction/pipeline.py`。
